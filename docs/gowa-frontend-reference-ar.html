01 ما هو هذا الـ service

الـ backend هو multi-device WhatsApp Web API server مكتوب بلغة Go 1.25 فوق Fiber v3، يتصل بـ WhatsApp عبر مكتبة whatsmeow، ويخزّن المحادثات في PostgreSQL وليس تخزيناً محلياً.

  • عدة أجهزة في process واحد: كل device هو whatsmeow session مستقلة لها device_id خاص بها، وكلها تعمل داخل نفس الـ server.
  • واجهتان للتشغيل: الـ REST mode هو الأساس، وهناك MCP mode لأدوات الـ AI. الواجهة الأمامية تستخدم الـ REST mode فقط.
  • الـ UI صار منفصلاً: منذ الإصدار v9 صار الـ dashboard مشروعاً مستقلاً يُنزَّل عند التشغيل، والـ backend صار pure API backend.
  • تكاملات جاهزة: Chatwoot bridge، وAI agent webhook، وvoice note transcription، وSMS fallback gateway.
الفكرة التي تحكم كل ما يلي: التحديثات الأخيرة أضافت ثلاثة محاور تحكّم فوق كل request — من أنت (principal)، وأي حساب (account scope)، وأي جهاز (device scope). أي request لا يضبط الثلاثة معاً يُرفض أو يرجع ببيانات ناقصة بصمت.

02 الشكل العام للـ API

الـ base path

كل الـ endpoints تُركَّب تحت APP_BASE_PATH (فارغ افتراضياً). في هذا المستند تُكتب المسارات بلا prefix؛ فإن كان الـ deployment يستخدم /gowa فالمسار الفعلي هو /gowa/chats وهكذا.

الاستثناء الوحيد هو GET /health — مسجَّل عند الجذر دائماً ليكون له عنوان ثابت لأي liveness probe مهما تغيّر الـ base path.

الـ response envelope

كل response — نجاحاً كان أو فشلاً — يخرج بنفس الشكل الثلاثي:

{
  "code":    "SUCCESS",        // a string code, never numeric
  "message": "Success get chat messages",
  "results": { /* omitted entirely when empty */ }
}

الـ HTTP status code يسافر في الـ status line لا داخل الـ body. والحقل results يحمل omitempty، فغيابه ليس خطأ — بل يعني أن العملية لا تُرجع بيانات، مثل POST /auth/logout.

المسارات العامة (بلا token)

هذه وحدها تعمل بلا authentication، وكل ما عداها محروس بـ Require(permission) مكتوبة على سطر الـ route نفسه:

  • GET / — الـ UI bundle، وإلا صارت شاشة الـ login غير قابلة للوصول.
  • GET /health — عند الجذر دائماً.
  • POST /auth/login وPOST /auth/refresh وPOST /auth/logout.
  • GET /api-docs وGET /api-docs/openapi.yaml.
  • POST /chatwoot/webhook — يصادق بـ shared secret خاص به.
ضمانة عند الـ boot: الـ server يرفض الإقلاع إن وُجد route واحد ليس في هذه القائمة ولا يحمل Require(...) — دالة AssertPolicyCoverage. فأي endpoint جديد محروس بالضرورة.

03 الـ authentication الجديد

الـ basic auth القديم أُزيل بالكامل. النظام الحالي هو JWT access token قصير العمر + opaque refresh token طويل العمر، وأربعة endpoints لا خامس لها.

الـ token pair

النوعالشكلالعمرملاحظات للواجهة
access_token JWT موقّع HS256 15 دقيقة يُرسل في Authorization: Bearer <token>. غير قابل للإلغاء قبل انتهائه.
refresh_token opaque، 256-bit random 30 يوماً (720h) ليس JWT ولا يحمل معلومات — لا تحاول فكّه. يُخزَّن في الـ DB كـ SHA-256 digest.

الـ access_token يحمل داخله ثلاثة claims مخصصة — account_id وepoch وsub — لكن لا تقرأها الواجهة من الـ token: الـ server يعيد بناء الـ role والـ permissions من الـ cache عند كل request، والمصدر الصحيح للواجهة هو GET /auth/me.

الـ endpoints الأربعة

POST /auth/login — عام

// request
{ "username": "admin", "password": "..." }

// response 200
{
  "code": "SUCCESS",
  "message": "Login successful",
  "results": {
    "access_token":  "eyJhbGciOi...",
    "refresh_token": "5Xk2...",
    "expires_in":    900,          // SECONDS, access token only
    "user": {
      "user_id":     "usr_01...",
      "username":    "admin",
      "account_id":  "acc_01...",
      "role":        "admin",
      "roles":       ["admin"],
      "permissions": ["chats.read", "messages.send", /* ... */],
      "status":      "active"
    }
  }
}

الحقل expires_in بالثواني ويصف الـ access token وحده. وُضع خصيصاً لتجدول الواجهة silent refresh بدل اكتشاف الانتهاء بـ 401 في منتصف عملية.

POST /auth/refresh — عام

{ "refresh_token": "5Xk2..." }   // returns a NEW pair

الـ refresh فيه rotation: كل استدعاء ناجح يُبطل الـ token القديم ويصدر زوجاً جديداً — فيجب على الواجهة أن تستبدل الاثنين معاً. واستعمال token مستهلَك مرتين يُبطل عائلة الـ tokens كلها (reuse detection)، فالنتيجة الصحيحة للواجهة هي logout كامل لا إعادة محاولة.

POST /auth/logout — عام

يأخذ نفس الـ body ويُبطل عائلة الـ refresh token بالكامل. هو عام عمداً: يقرأ الـ body فقط ولا يقرأ الـ principal، حتى تستطيع session انتهى access token خاصها أن تُلغي refresh token عمره 30 يوماً.

GET /auth/me — يتطلب مصادقة فقط

هذا هو الـ endpoint الذي تُبنى عليه الواجهة. يرجع نفس كائن user أعلاه — وعلى رأسه مصفوفة permissions النهائية بعد دمج كل الـ roles. القاعدة: ارسم الأزرار من هذه المصفوفة، لا من اسم الـ role، لأن الـ roles صفوف في قاعدة البيانات ويمكن للـ operator تركيب role رابع بلا إعادة نشر.

الـ rate limiting

المفتاح هو الـ TCP peer لا الـ X-Forwarded-For، فخلف reverse proxy قد يتشارك كل العملاء نفس الـ bucket — تعامل مع الـ 429 كحالة واردة فعلاً.

الـ token epoch — الحالة التي تفاجئ الواجهات

لكل مستخدم عدّاد token_epoch. أي تعديل إداري عليه — تغيير الـ roles، أو الـ status، أو الـ account، أو إعادة تعيين الـ password — يزيد العدّاد ويُبطل فوراً كل access و refresh tokens القائمة.

النتيجة على الواجهة: مستخدم يعمل بشكل طبيعي قد يتلقى 401 فجأة، والـ refresh لن ينقذه. المعالجة الصحيحة: عند 401 جرّب refresh مرة واحدة، فإن فشل → امسح الـ session واعرض شاشة login برسالة «تم تحديث صلاحياتك».

سلوك الـ middleware — مهم لفهم رموز الأخطاء

  • الـ Authenticate middleware يُعرِّف ولا يرفض: token غائب أو تالف أو منتهٍ يمرّ كـ anonymous request.
  • الرفض يحدث في Require(permission) على سطر الـ route — لهذا قد يأتي 401 من route محروس لا من الـ auth layer.
  • ولهذا أيضاً يعمل /auth/login حتى لو أرسلت الواجهة token قديماً بالخطأ — وهي الحالة التي يجب أن تعمل دائماً.

04 الأدوار والصلاحيات (RBAC)

الـ permissions ثوابت في الكود (compile-time) — تُنسخ إلى جدول عند الـ boot ليكون للـ grants ما تشير إليه. أما الـ roles فصفوف، لذا يستطيع الـ operator تركيب role جديد بلا redeploy. ومن هنا القاعدة الذهبية للواجهة: اعتمد على permissions[] لا على اسم الـ role.

05 طبقة الـ account

الـ account هي الطبقة التي أُضيفت فوق الأجهزة: حساب واحد يجمع عدة devices، فإذا تعذّر إرسال رد من الجهاز الذي وصلت عليه الرسالة، يخرج الرد من جهاز شقيق (sibling device) في نفس الحساب.

وهي أيضاً حدّ العزل بين العملاء: كل مستخدم ينتمي إلى account_id واحد، وكل ما يراه محصور به. القيمة الفارغة "" ليست «بلا حساب بعد» بل تعني لا يملك شيئاً — ولهذا يرفض النظام إنشاء مستخدم بحساب فارغ.

كائن الـ Account

{
  "account_id":           "acc_01H...",
  "name":                 "Acme Support",
  "sms_fallback_enabled": false,   // ALWAYS present, no omitempty
  "created_at":          "2026-01-14T09:12:00Z",
  "updated_at":          "2026-02-02T11:40:00Z"
}

لا يوجد ولن يوجد حقل meta_token_ref في أي response — الحقل غير موجود على الـ struct أصلاً، لا مخفياً بـ tag.

الـ SMS fallback

عند تفعيله على الحساب، إذا فشلت كل قنوات WhatsApp، يخرج POST /send/message عبر SMS gateway. أثره على الواجهة حقل واحد في الـ response: 

{
  "message_id": "3EB0...",   // carrier ref, MAY BE EMPTY, when channel=sms
  "status":     "...",
  "channel":    "whatsapp"  // or "sms" — omitempty, only on /send/message
}
قاعدة إلزامية: اقرأ channel قبل استعمال message_id. عند channel === "sms" لا وجود لرسالة WhatsApp ولا صف في الـ chat storage — فلا تنتظر ظهورها في GET /chat/{jid}/messages، ولا تبنِ عليها reply أو reaction.

06 الأجهزة والـ device scoping

كيف يُختار الجهاز في كل request

معظم الـ endpoints التشغيلية تحتاج جهازاً، ويُحدَّد بأحد طريقين:

  1. الـ header X-Device-Id: acme-prod-1 — الطريقة الموصى بها.
  2. الـ query ?device_id=acme-prod-1 — بديل عند تعذّر الـ headers.

إن لم يُذكر أي منهما، يحاول الـ server استخدام الجهاز الافتراضي الوحيد. وإن تعذّر ذلك — أو كان الافتراضي يخص حساباً آخر — يرجع 400 DEVICE_ID_REQUIRED.

القاعدة الأمنية التي تغيّر شكل معالجة الأخطاء: جهاز يخص حساباً آخر يُجاب بـ 404 DEVICE_NOT_FOUND — نفس الـ body بايت ببايت الذي يعطيه جهاز غير موجود أصلاً. لا يُستخدم 403 هنا إطلاقاً لأنه سيؤكد وجود الجهاز. لذلك: لا تعرض للمستخدم «ليس لديك صلاحية على هذا الجهاز» — الـ backend لا يخبرك بذلك عمداً، وكل ما تعرفه هو «غير متاح».

الـ 404 يُعيد صدى الـ id الذي أرسلته أنت لا الـ id الذي حُلَّ داخلياً — مفيد عند إرسال دفعة requests لمعرفة أيها فشل.

الـ metadata_debug وآلية الـ opt-in

الحقل يرجع داخل الـ response، لكن ظهوره مشروط بـ query parameter اسمه include_debug:

  • الصلاحية تسبق الـ parameter: من لا يملك messages.debug.read ويرسل include_debug=true يُتجاهل بصمت — لا 403 — وتختفي الحقول كلياً.

09 الـ redaction — الحقول التي تختفي

هذه أهم فقرة في المستند بالنسبة للواجهة. الحجب في هذا الـ backend حذف للمفتاح وليس null ولا false ولا نصاً فارغاً. الحقول التالية تغيب كلياً من الـ JSON عندما لا يملك المستخدم صلاحيتها: metadata_debug، has_debug، transcript، transcript_language، transcript_status، sent_by، sent_by_name.

لماذا صُمم هكذا

لو رجع has_debug: false لكل رسالة، لكان ذلك تصريحاً دائماً بوجود حقل لا يحق للمستخدم رؤيته. بغياب المفتاح، لا يستطيع المستخدم التمييز بين «لا توجد diagnostics» و«لا يحق لك رؤيتها» — وهذا هو المطلوب أمنياً.

ما يعنيه هذا عملياً في الكود

// WRONG — a privileged user with no diagnostics looks identical
if (message.has_debug === false) showNothing()

// WRONG — "sent_by" is absent, not empty
const sender = message.sent_by || "unknown"

// RIGHT — presence of the KEY is the signal
const canSeeOrigin = "sent_by" in message
const hasDebug     = message.has_debug === true

وحتى للمستخدم صاحب الصلاحية، has_debug يحمل omitempty — فغيابه يعني «لا توجد diagnostics»، وهو ما كان يعنيه false سابقاً. لا تنتظر false صريحة أبداً.

القاعدة العامة للواجهة

  • ارسم واجهة الـ diagnostics و الـ transcript و الـ origin شرطياً من permissions[] في /auth/me، لا من محتوى الرسالة.
  • ثم تعامل مع غياب المفتاح على أنه «لا يوجد» بلا رسالة خطأ — لأن الـ backend لن يفرّق لك بين الحالتين.
  • الحقل sent_via ليس ضمن المحجوبات: يمكنك دائماً تمييز الرد الآلي عن رد الإنسان حتى بلا messages.origin.read.

10 الـ WebSocket والأحداث

الاتصال

الـ endpoint هو /ws ويتطلب مستخدماً مصادقاً عليه. وبما أن الـ browser WebSocket API لا يسمح بإرسال headers، يُمرَّر الـ token في الـ query: 

ws://host/ws?access_token=<the access token>

الـ server يرفع الـ parameter إلى Authorization header داخلياً ثم يحذفه من الـ URL حتى لا يتسرب إلى الـ logs. وبما أن الـ access token يعيش 15 دقيقة، على الواجهة إعادة فتح الـ socket بعد كل refresh — لأن الـ principal يُلتقط مرة واحدة عند الـ handshake ولا يُعاد قراءته.

الـ principal مُجمَّد عند الـ handshake. تغيير أدوار مستخدم لن يؤثر على socket مفتوح حتى يُعاد فتحه. اجعل إعادة الاتصال جزءاً من دورة الـ refresh.

الـ fan-out معزول بالحساب

كل رسالة بث تحمل داخلياً account_id، ولا تصل إلا إلى الـ sockets التي يحق لأصحابها مخاطبة ذلك الحساب. سابقاً كان اتصال /ws واحد يستقبل أحداث كل الحسابات — وهذا انتهى.

11 قائمة التعديلات المطلوبة على الواجهة

الواجهة الحالية تعرض المحادثات وتعمل — لكنها بُنيت قبل هذه الطبقات. هذه قائمة العمل مرتبة بالأولوية:

أولوية عالية — بدونها لا تعمل الواجهة

  1. استبدال الـ basic auth بالكامل. لم يعد موجوداً في الـ backend. أضف شاشة login تستدعي POST /auth/login، وخزّن الزوج، وأرسل Authorization: Bearer مع كل request.
  2. طبقة silent refresh. جدولة تجديد قبل انتهاء expires_in، مع interceptor يعالج الـ 401: محاولة refresh واحدة، فإن فشلت → logout كامل. واستبدل كلا الـ tokens بعد كل refresh (rotation).
  3. إرسال X-Device-Id في كل request تشغيلي. مع اختيار جهاز واضح في الواجهة، ومعالجة DEVICE_ID_REQUIRED وDEVICE_NOT_FOUND كحالتين مختلفتين.
  4. إعادة فتح الـ WebSocket بعد كل refresh، وتمرير الـ token عبر ?access_token=.

أولوية متوسطة — سلامة العرض والصلاحيات

  1. بناء الـ UI من permissions[] القادمة من /auth/me — إخفاء صندوق الإرسال لدور user، وإخفاء أزرار pin/archive بلا chats.write، وإخفاء سطح الإدارة بلا accounts.manage / users.manage.
  2. مراجعة كل قراءة لحقل محجوب واستبدال فحص القيمة بفحص وجود المفتاح (فقرة 09) — هذا أكثر ما يسبب أخطاء صامتة.
  3. معالجة الـ token epoch: رسالة واضحة عند الخروج القسري بعد تعديل إداري، بدل رسالة خطأ عامة.

ميزات جديدة يمكن للواجهة كشفها

  1. لوحة الـ metadata_debug: شارة عند has_debug، وعند النقر إمّا الـ payload المُضمَّن أو استدعاء GET /message/{id}/debug. اجعل include_debug اختياراً صريحاً لا افتراضاً في كل page load.
  2. عرض الـ transcript تحت مشغّل الرسالة الصوتية — لا بدلاً منه، فالصوت يبقى كما هو ويبقى قابلاً للتنزيل.
  3. شارة أصل الرسالة من sent_via (رد آلي / موظف / Chatwoot)، واسم المُرسِل عند توفر sent_by_name.
  4. سطح إدارة الحسابات: ترتيب الأجهزة بالسحب (priority)، وحجب جهاز (send_state)، ومفتاح الـ SMS fallback.
  5. سطح إدارة المستخدمين: إنشاء، تعديل، إعادة تعيين كلمة مرور، مع عرض واضح لرفضات self-mutation و privilege escalation.
  6. وسم رسائل الـ SMS: عند channel === "sms" اعرضها كقناة مختلفة، ولا تنتظر ظهورها في سجل المحادثة.
