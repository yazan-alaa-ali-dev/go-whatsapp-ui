دليل المهندس إلى واجهة gowa-ui

قراءة معمارية للمشروع من منظور backend engineer: ما هو، كيف يُبنى الكود، وكيف تبدأ التطوير عليه اليوم دون أن تكسر قيوده.

البناء Vite 8 الإطار React 19 اللغة TypeScript 6 التنسيق Tailwind 4 المكوّنات shadcn/ui المخرَج ملف HTML واحد

الجواب المباشر: هل هو Next.js؟

لا. المشروع TypeScript نعم، لكنه ليس Next.js.

هو SPA خالص مبني بـ Vite + React 19، بلا SSR وبلا server runtime وبلا API routes. لا يوجد مجلد app/ ولا pages/ بمعنى Next، ولا next.config، والتوجيه يتم عبر react-router-dom.

السبب معماري وليس ذوقياً: الهدف النهائي هو ملف HTML واحد اسمه gowa-ui.html بلا أي طلب خارجي، يستضيفه أي static host أو يقدّمه خادم gowa نفسه على المسار /. هذا القيد يجعل vite-plugin-singlefile ضرورة، ويجعل Next.js — بكل ما فيه من server-side runtime — خياراً غير متوافق أصلاً.

ما هذا المشروع بالضبط

واجهة تحكم لخادم go-whatsapp-web-multidevice — المعروف اختصاراً باسم gowa. الـ backend يبقى REST API نقي، والواجهة تُشحن منفصلة تماماً وتتصل به من المتصفح مباشرة. لا توجد أي طبقة backend داخل هذا المستودع: لا proxy إنتاجي، ولا session server، ولا قاعدة بيانات.

عملياً هذا يعني أن كل ما تراه في src/api/ هو عقد (contract) مع خادم Go خارجي، وأن أي تغيير في ذلك الخادم يظهر هنا كتعديل في path أو في شكل الـ payload، لا أكثر.

خريطة البنية

التنظيم feature-first وليس type-first: الشاشة تجمع مكوّناتها، والمنطق المشترك فقط هو الذي يصعد إلى الأعلى. القاعدة العملية — لو حذفت ميزة كاملة، يجب أن يكفي حذف مجلدها ومساراتها.

كيف يُكتب الكود هنا — مسار الطلب كاملاً

أهم نمط في المستودع: الطلب يُوصَف قبل أن يُرسَل. كل endpoint يبني كائن ApiRequest، ثم يُنفَّذ ذلك الكائن أو يُعرض كأمر curl — فلا ينحرف الاثنان عن بعضهما أبداً. هذا تسلسل حقيقي، اتبعه بالترتيب:

النموذج في features/ يجمع الحقول

حالة محلية عبر useState فقط. النموذج لا يعرف axios ولا المسارات — يعرف دالة واحدة يستدعيها.

دالة xRequest() في api/ تصف الطلب

تُرجع { method, path, json | form }. الحقول الفارغة تُنظَّف عبر clean() حتى لا يرى الخادم إلا ما ضُبط فعلاً.

exec() يحوّل الوصف إلى استدعاء

وجود form يعني FormData تلقائياً — وهو المسار الوحيد لرفع الملفات. غير ذلك JSON.

interceptors في lib/http.ts تحقن السياق

الـ baseURL والمصادقة و X-Device-Id تُضاف هنا مركزياً. لا تمرر هذه القيم يدوياً في أي مكان آخر.

results() يفكّ الغلاف

المكوّن يستلم results مباشرة، لا الغلاف. وأي 401 يُترجم إلى markUnauthorized() في connection store.

useActionMutation يوحّد النتيجة

نجاح ⇐ toast، فشل ⇐ toApiError() ثم toast خطأ. لا تكتب معالجة أخطاء يدوية في النماذج.

الشكل النموذجي لـ endpoint

// src/api/send.ts — زوج ثابت: وصف + تنفيذ
export function textRequest(payload: TextPayload): ApiRequest {
  return { method: 'POST', path: '/send/message', json: clean(payload) }
}

export function sendText(payload: TextPayload): Promise<SendResult> {
  return exec(textRequest(payload))
}

إدارة الحالة — ثلاث طبقات لا تتداخل

الطبقةالأداةما يوضع فيها
حالة الخادم react-query قوائم الأجهزة والمجموعات والمحادثات — أي شيء يُجلب ويُبطَّل
حالة عميل دائمة zustand + persist connection، device، recipient
حالة النموذج useState حقول الإدخال، التبويب النشط، فتح الحوارات

لا توجد مكتبة forms مثل react-hook-form، ولا zod. التحقق يتم بسمات HTML الأصلية (required) وبتعطيل زر الإرسال. حافظ على ذلك — إدخال مكتبة جديدة يضخّم حجم الملف الواحد بلا مقابل.

الأحداث اللحظية

lib/ws.ts يحتوي عميل WebSocket واحد يعيد المصالحة مع connection و device عبر sync()، مع exponential backoff عند الانقطاع. الأحداث تُبثّ عبر onWsEvent، و App.tsx يترجم رموزاً مثل LOGIN_SUCCESS و DEVICE_REMOVED إلى invalidateQueries. هذا هو الجسر بين الدفع اللحظي والـ cache.

القواعد الملزِمة — ما يكسر البناء

قيد الملف الواحد

ممنوع import() الديناميكي و React.lazy — أي code splitting يكسر مخرَج الملف الواحد. وممنوع أي CDN script أو خط بعيد أو صورة خارجية: كل شيء يُحزَم ويُضمَّن.

التوجيه

HashRouter فقط. هو الوحيد الذي يعمل من file:// ومن أي مسار تركيب. لا تستبدله بـ BrowserRouter.

التحقق الآلي

الـ CI يشغّل typecheck و lint و build، ثم يتأكد أن dist/ يحتوي ملفاً واحداً بالضبط. أي أصل غير مضمَّن يسقط الـ pipeline فوراً.

أسلوب الكتابة المتبع

  • Prettier: بلا فاصلة منقوطة، علامات اقتباس مفردة، عرض ١٠٠ حرف.
  • ملفات وأسماء بصيغة kebab-case، ومكوّنات بـ PascalCase.
  • الاستيراد دائماً عبر الاسم المستعار @/ لا عبر مسارات نسبية طويلة.
  • export default للصفحات فقط؛ كل شيء آخر named export.
  • الاختبارات مجاورة للملف: lib/jid.ts يقابله lib/jid.test.ts.
  • الاختبارات تغطي المنطق النقي فقط — jid، curl، backoff، format، url.
  • التعليقات تشرح لماذا لا ماذا، وهي نادرة ومقصودة.

٤ · أضف endpoint جديداً — التمرين الأول المقترح

هذا أقصر طريق لفهم المعمار عملياً. الخطوات بالترتيب، وكل واحدة تلمس طبقة واحدة فقط:

  • عرّف الـ types في src/api/types.ts إن كانت مشتركة.
  • أضف زوج xRequest() و x() في ملف api/ المناسب.
  • ابنِ النموذج في features/<domain>/ واستخدم useActionMutation.
  • ذيّل النموذج بـ FormActions ومرر له request ليعمل زر cURL تلقائياً.
  • اعرض الناتج عبر ResultPanel، وركّب النموذج داخل الصفحة.
  • شغّل typecheck ثم build قبل الـ commit.

٥ · مهام مفتوحة فعلاً

حسب خارطة الطريق في README، المتبقي بندان واضحان: وحدة Chatwoot config — ولاحظ أن AppInfo يحمل أصلاً الحقل chatwoot_enabled — وإكمال تدفق WebAuthn passkey الذي يوجد له حالياً حوار ورموز PASSKEY_* في طبقة الأحداث دون تدفق كامل.

ملاحظات لمهندس backend تحديداً

  • هوية المستلم تُبنى في lib/jid.ts: الرقم يُلحق بلاحقة حسب النوع — @s.whatsapp.net للأفراد، @g.us للمجموعات، @newsletter للقنوات، @lid، أو status@broadcast. إن ورد @ في المدخل يُترك كما هو.
  • زر Copy cURL في كل نموذج مبني من نفس كائن الطلب، فهو أداة تشخيص موثوقة عند التحقيق في اختلاف سلوك بين الواجهة والخادم.
  • شاشة الاتصال تميّز خادم gowa الحقيقي عن أي خادم يردّ 200، عبر فحص وجود الحقل code في جسم /devices.
  • يوجد وضع zero-config: إن كانت الصفحة مقدَّمة من gowa نفسه، يُجرَّب الـ same origin تلقائياً ويعيد المتصفح بيانات الاعتماد المخزّنة.
  • الإصدار: وسم v* ينشر أصلاً واحداً باسم gowa-ui.html مع .sha256. الاسم جزء من العقد مع الـ backend — لا تغيّره.
